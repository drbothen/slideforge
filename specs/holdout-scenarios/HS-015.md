# HS-015: Watch Mode HTTP Failure — API Goes Down Mid-Session

## Objective

Validate FM-005 and DEC-007: when an HTTP data source becomes unreachable mid-session
during watch mode, slideforge handles the failure gracefully — emitting a structured
error, preserving the last valid preview state, and recovering automatically when the
data source comes back online.

## Scenario Description

A deck in watch mode fetches metrics from a mock HTTP server:

```sf
@data metrics from "http://localhost:9877/q3-metrics.json"

slide stat_callout:
  heading "Revenue"
  value "{{ metrics.revenue | format_currency }}"
  delta "{{ metrics.revenue_delta }}%"
```

**Phase 1 (stable):** The mock server is running. Initial build succeeds; web preview
shows the metrics slide correctly.

**Phase 2 (outage):** The mock server is stopped (TCP connection refused). The .sf
source file is saved (triggering a rebuild). Rebuild fails because the HTTP source
is unreachable.

**Phase 3 (recovery):** After 10 seconds, the mock server is restarted. The .sf source
file is saved again (or auto-retry fires). The rebuild succeeds.

## Expected Postconditions

1. Phase 2 rebuild emits E-DAT-005 (HTTP fetch failure) with URL and error type
   ("Connection refused").
2. Web preview in Phase 2 continues showing the LAST VALID slides — not a blank screen
   and not a "no preview available" error page.
3. The watch CLI does NOT exit during Phase 2; it remains in the watching state.
4. The CLI output in Phase 2 includes the error and a hint: "Use --offline to build
   with last cached data."
5. Phase 3: after the mock server restarts and a rebuild is triggered, the build
   succeeds and the web preview updates to reflect fresh data.
6. No partial or corrupted output files are written during Phase 2.

## Evaluation Criteria

| Criterion | Weight | PASS condition |
|-----------|--------|---------------|
| E-DAT-005 emitted with URL | CRITICAL | Error code and URL present in diagnostics |
| Last valid preview preserved | CRITICAL | Browser shows previous slides |
| CLI stays alive (no exit) | CRITICAL | Process continues running |
| Offline hint in error message | HIGH | "Use --offline" text visible in CLI output |
| Phase 3 recovery succeeds | HIGH | Rebuild succeeds; preview updates |
| No corrupted output files | HIGH | No partial .pptx written during Phase 2 |

## Information Asymmetry Note

This is a non-must-pass resilience scenario. The implementer sees BC-1.03.002
(HTTP data source) and BC-1.03.004 (--offline flag) but does NOT see this watch-mode
failure/recovery sequence. The hidden integration point is that the "last valid state
preservation" behavior requires coordination between the HTTP data source plugin, the
error recovery system, and the WebSocket preview server — three separate subsystems that
must cooperate correctly under failure conditions.
