# HS-011: Performance Gate — 25-Slide Deck with 5 @data Sources Under 500ms

## Objective

Validate ASM-011 and R-005: the 500ms cold build target for a 25-slide deck is
achievable without comemo incremental compilation. This is a hard CLAUDE.md
quality gate.

## Scenario Description

A 25-slide deck that stresses the most expensive parts of the pipeline:
- 5 file-based @data sources (JSON, CSV, YAML, TOML, one large file)
- Slides using 10 different slide types
- 3 chart slides (plotters rendering)
- 2 diagram slides (mermaid-rs-renderer, cold font scan amortized)
- 1 variant (filter by tags)
- Brand synthesized from brand.toml (not a pre-built .pptx)

Run on: Linux x86_64 CI (GitHub Actions ubuntu-latest runner).

## Input

**`perf-deck.sf`**: 25-slide deck as described.
**5 data files**: total JSON/CSV/YAML data load ≈ 50KB.
**`brand.toml`**: complete brand with all 12 color slots.

## Expected Postconditions

1. `slideforge build perf-deck.sf --format pptx` exits 0.
2. Total wall-clock build time < 500ms (measured from CLI invocation to process exit).
3. Per-stage breakdown available via `--verbose`: parse < 50ms, evaluate < 30ms, layout < 150ms, export < 200ms.
4. Output .pptx is valid (not a partial/corrupt file from a fast exit).

## Evaluation Criteria

| Criterion | Weight | PASS condition |
|-----------|--------|---------------|
| Total build < 500ms | CRITICAL | Wall-clock time measurement |
| Valid output produced | CRITICAL | PPTX opens; not corrupt |
| Per-stage timing within bounds | MEDIUM | parse + eval + layout + export < 500ms total |

## Notes

If this scenario fails, the architect must evaluate:
1. Whether comemo incremental compilation should move from v1.x to v1.0 scope.
2. Whether parallel export (concurrent format rendering) can close the gap.
3. Whether the 31-type layout computation can be cached (memoized) across slides.

Per CLAUDE.md: this is a release blocker. "< 500ms cold build for 25-slide deck
enforced in CI as a benchmark gate."
