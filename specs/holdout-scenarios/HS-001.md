# HS-001: DSL User Acceptance — Engineering Team Produces Q3 Report Deck

## Objective

Validate ASM-001: engineering teams accept the indentation-significant DSL as their
primary authoring interface. This scenario simulates an engineer authoring a realistic
25-slide branded quarterly report from scratch using only the DSL documentation.

## Scenario Description

An engineer with familiarity with Python and YAML (but no prior slideforge experience)
is given:
1. The slideforge binary (pre-built)
2. The DSL reference documentation
3. A brand.toml for their company

They are asked to author a Q3 business review deck (25 slides) covering:
- Executive summary (title + content slides)
- Financial performance (stat_callout + chart slides)
- Incident summary (severity_cards + @for data binding from incidents.json)
- Technical highlights (content + diagram slides)
- Roadmap (timeline slide)
- Q4 plan (numbered_actions slide)

## Input Files

**`q3-review.sf`** (to be authored by evaluator):
- Uses at least 8 different slide types
- At least 2 @data sources (JSON files)
- At least 1 @for loop
- At least 1 variant (exec vs full)
- Brand.toml with complete company brand

**`incidents.json`:** 3 incident records with id, severity, title, resolution fields

**`financial.json`:** Quarterly revenue, growth, and cost metrics

## Expected Postconditions

1. `slideforge build q3-review.sf --format pptx,docx` exits 0.
2. Output `.pptx` opens in LibreOffice without error dialogs.
3. Output `.pptx` has ≥ 20 slides with visible content on each.
4. Output `.docx` has the report register content as body paragraphs.
5. No accessibility errors (all visual elements have alt text declared).
6. `slideforge build q3-review.sf --variant exec` produces a deck with ≤ 15 slides (executive audience filtering works).
7. Build time < 500ms (NFR-001).
8. Zero validation errors in strict mode.

## Evaluation Criteria

| Criterion | Weight | PASS condition |
|-----------|--------|---------------|
| Build succeeds without errors | HIGH | Exit 0, both formats written |
| Content appears correct in PPTX | HIGH | Each slide type has its data populated |
| Variant filtering works | MEDIUM | exec variant has fewer slides than full |
| Build time < 500ms | HIGH | Measured wall-clock |
| DSL was learnable from docs alone | MEDIUM | Evaluator required < 3 doc lookups per slide type |

## Notes

This is the primary acceptance test for ASM-001. If it fails, the DSL is not
learnable/acceptable and the product premise requires re-evaluation.
