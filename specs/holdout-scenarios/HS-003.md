# HS-003: HTTP Data Source Schema Change During Watch Mode

## Objective

Validate FM-005 and DEC-018: when an HTTP data source returns a changed schema
during watch mode, slideforge detects the structural mismatch, emits a structured
error, and continues serving the last valid state — without crashing or silently
producing slides with missing data.

## Scenario Description

A deck in watch mode fetches live incident data from a mock HTTP server:

```sf
@data incidents from "http://localhost:9876/incidents.json"

@for item in incidents:
  slide severity_cards:
    title "{{ item.title }}"
    severity "{{ item.severity }}"
    ...
```

**Phase 1 (initial):** The mock server returns 3 incidents with fields
`{id, title, severity, resolution}`. Initial build succeeds.

**Phase 2 (schema change):** After 5 seconds, the mock server begins returning
incidents WITHOUT the `severity` field (simulating a backend API breaking change).
Watch mode triggers a rebuild.

## Expected Postconditions

1. The rebuild triggered by the schema change emits E-DAT-003 (missing field access).
2. The watch mode CLI displays the error with source span: `item.severity` line and
   column, and the note "field 'severity' not found in schema".
3. The browser web preview continues showing the LAST VALID slides (not a blank screen,
   not slides with missing data).
4. The watch CLI does NOT crash or exit (process remains running).
5. When the mock server reverts to the original schema, the next rebuild succeeds and
   the web preview updates correctly.
6. Total time from schema revert to preview update is < 2 seconds.

## Evaluation Criteria

| Criterion | Weight | PASS condition |
|-----------|--------|---------------|
| E-DAT-003 emitted on schema change | CRITICAL | Structured error with source span |
| Last valid state preserved in browser | CRITICAL | Preview shows previous slides, not blank |
| CLI does not crash | CRITICAL | Process still running; accepts keyboard input |
| Recovery after schema fix | HIGH | Rebuild succeeds; preview updates < 2s |
| Error message names missing field | HIGH | "severity" named explicitly in error |

## Information Asymmetry Note

The implementer sees BC-1.03.002 (HTTP data source load) and BC-1.03.004 (--offline flag)
but does NOT see this scenario. The "last valid state preservation" requirement is a
watch-mode resilience property that tests the boundary between the error recovery system
and the WebSocket preview server — a cross-subsystem integration not covered by any single BC.
