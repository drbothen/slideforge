# STORY-027: Layout — Document Section Generation (DOCX)

## Subsystem Anchor Justification

SS-05 (Layout Engine) owns section generation because section ordering and content
collection from the `Deck` IR happens in the layout stage — after evaluation resolves
all `{{ expr }}` and `@data` bindings. SS-08 (DOCX Export) only serializes what the
layout stage has already assembled. Per ARCH-INDEX Subsystem Registry, SS-05 is the
single point of section assembly.

## Dependency Anchor Justifications

- Depends on STORY-026: `LaidOutDeck` structure must exist before section data can
  be appended to it. The `LaidOutSlide` type from STORY-026 is the input to section
  collection.
- Blocks STORY-041 (DOCX core serialization) and STORY-042 (DOCX auto-sections):
  those stories consume `GeneratedSection` data that this story produces in the
  layout IR.

## Summary

Extend the layout stage to collect and assemble document sections for DOCX/PDF output:

1. **Auto-generated sections**: Collect `takeaway` fields from contributing slide
   types to produce `executive_summary`. Collect `severity_cards` slides to produce
   `risk_register`. (BC-3.02.001)

2. **Manually authored sections**: Parse `section <type>:` blocks already in the
   `Deck` IR and include them in the `LaidOutDeck`'s section list. (BC-3.02.002)

Section data is added to `LaidOutDeck` as a `Vec<GeneratedSection>`. Exporters
(DOCX, PDF) consume this without re-parsing the source.

## Acceptance Criteria

### AC-001: Auto-generated executive_summary from takeaway fields
(traces to BC-3.02.001 postcondition 2)

When a `Deck` contains slides with a `takeaway:` field, `layout::run()` collects
those takeaway strings in slide order and places them in a `GeneratedSection`:
```rust
GeneratedSection {
    kind: SectionKind::ExecutiveSummary,
    source: SectionSource::AutoGenerated,
    items: vec![
        SectionItem::TakeawayBullet("Takeaway text from slide 1".into()),
        SectionItem::TakeawayBullet("Takeaway text from slide 3".into()),
    ],
    heading: "Executive Summary".into(),
}
```
The `GeneratedSection` is appended to `LaidOutDeck.sections`.

### AC-002: Auto-generated risk_register from severity_cards slides
(traces to BC-3.02.001 postcondition 3)

When a `Deck` contains `slide severity_cards:` blocks, each card entry (title,
severity, description, owner) is collected into `SectionItem::RiskRow` entries.
Multiple severity_cards slides produce multiple rows in the same `risk_register`
section. De-duplication is NOT applied (BC-3.02.001 EC-003).

### AC-003: Section omitted when no contributing slides
(traces to BC-3.02.001 postcondition 5)

If no slides in the `Deck` contain `takeaway:` fields, no `ExecutiveSummary` section
is added to `LaidOutDeck.sections`. If no `severity_cards` slides exist, no
`RiskRegister` section is added. Zero empty section headings are produced.

### AC-004: Manual section blocks appear in LaidOutDeck
(traces to BC-3.02.002 postcondition 1)

`section <type>:` blocks in the `Deck` IR (top-level blocks, not nested inside
slides) are collected into `GeneratedSection { source: SectionSource::Manual, ... }`
entries. Supported types: `methodology`, `scope`, `approval`, `appendix`,
`glossary`. Unrecognized type produces `LayoutError::UnknownSectionType { name }`.

### AC-005: Manual sections excluded from PPTX and web preview
(traces to BC-3.02.002 postcondition 3)

`GeneratedSection` entries are tagged with `target_formats: [Docx, Pdf]`. Exporters
(PPTX, HTML) filter out any section where `target_formats` does not include their
format. This filtering is the exporter's responsibility, but the tag is set here.

### AC-006: Manual supersedes auto when both present
(traces to BC-3.02.001 precondition 3 — manual section supersedes auto-generated)

When a `Deck` contains both auto-generating slides (e.g., `takeaway:` fields) AND
an explicit `section executive_summary:` block, the manual section is retained and
the auto-generated section is suppressed. A lint warning is accumulated:
`"Auto-generated executive_summary overridden by explicit section block"`.

### AC-007: Section ordering
(traces to BC-3.02.001 postcondition 4)

Auto-generated sections appear at the end of `LaidOutDeck.sections` by default (after
all manual sections). If `section_order:` is declared in the deck metadata, sections
are ordered accordingly. `section_order:` is an ordered list of section type names.

## Previous Story Intelligence

This story extends STORY-026's `layout::run()`. The lesson from STORY-026 is that
`LaidOutDeck` must own all format-conditional data via tagging (not separate structs
per format). `GeneratedSection.target_formats` follows this pattern.

## Architecture Compliance Rules

1. **SS-05 pure core**: No file I/O in section collection. All data comes from the
   `Deck` IR passed into `layout::run()`.
2. **SectionType trait (DI-008)**: Section rendering in DOCX/PDF is delegated to
   `SectionType` plugin implementations. The layout stage only assembles
   `GeneratedSection` data — it does NOT render Word XML.
3. **DI-012 (single source for all formats)**: Same `LaidOutDeck.sections` is
   consumed by both DOCX and PDF exporters. No format-specific branching in layout.
