# Spike S2 — PDF Backend Evaluation

## Executive Summary

slideforge v1.0 requires PDF/UA-1 compliance (veraPDF must pass — quality bar is
non-negotiable). This spike evaluates five candidate approaches for the `slideforge-pdf`
exporter crate (Phase 4). The PDF exporter consumes `LaidOutDeck` — pre-positioned
shapes with EMU coordinates, semantic type tags, and alt-text — and must render them to
PDF pages.

**Recommended approach:** `pdf-writer` (low-level, by Typst's author, Laurenz Villiger)
with `krilla` as the mid-level drawing layer, plus a custom tagged-PDF engine implemented
in `slideforge-pdf`. The tagged-PDF layer must be built regardless of which low-level
library we use, since no Rust crate currently ships a production-grade PDF/UA-1 API.

**The PDF/UA-1 constraint is the decisive evaluation axis.** Every candidate except Typst
either (a) cannot produce tagged PDFs at all, or (b) can produce them only with
substantial custom work. Typst itself produces PDF/UA-1 but cannot accept pre-positioned
IR as input — it requires driving the Typst layout engine, which contradicts our Two-IR
architecture.

---

## Background: What the PDF Exporter Must Do

The `slideforge-pdf` exporter receives a `LaidOutDeck`:

```
LaidOutDeck {
    slides: Vec<LaidOutSlide>,    // one per output page
    metadata: DeckMetadata,       // title, lang, author
}

LaidOutSlide {
    size: (Emu, Emu),             // 9144000 x 5143500 for 16:9
    elements: Vec<LaidOutElement>,
    semantic_type: SlideType,     // title, content, etc.
    reading_order: Vec<ElementId>, // logical order for screen readers
}

LaidOutElement {
    id: ElementId,
    bounds: Rect<Emu>,            // x, y, width, height in EMU
    kind: ElementKind,            // Text, Image, Shape, Chart, Table
    alt: Option<String>,          // required for non-text
    semantic_role: SemanticRole,  // Heading, Paragraph, ListItem, Figure, etc.
    // ...
}
```

The exporter must:

1. Map EMU coordinates to PDF user units (1 point = 12700 EMU)
2. Embed fonts with ToUnicode CMaps for search/copy/paste/a11y
3. Embed SVG charts (generated by `plotters`) as vector content
4. Produce a PDF with a `/StructTreeRoot` containing a logical structure tree
5. Tag every element with `/MCID` and link to the structure tree
6. Set document language, title, and `/MarkInfo`
7. Pass `veraPDF --flavour ua1` validation

## Candidate Assessments

### Candidate 1: printpdf (v0.8.1)

**Author:** Felix Schütt (fschutt) — unaffiliated with Typst  
**Latest version:** 0.8.1 (2024–2025, sporadic maintenance)  
**License:** MIT  
**Unsafe code:** Minimal — mostly safe Rust; some image/font dependencies use unsafe internally

#### What it can do

- Embed TrueType/OpenType fonts with `/ToUnicode` CMaps and subset embedding
- Embed PNG and JPEG raster images (via `image` crate)
- Draw vector primitives: lines, rectangles, Bezier curves, fills, strokes
- Set document metadata (Info dictionary)
- Draw multi-page documents

#### What it cannot do

- **No tagged PDF / structure tree support.** There is no API for `/StructTreeRoot`,
  `/StructElem`, `/MCID`, `/RoleMap`, or `/MarkInfo`. These objects are not representable
  through printpdf's public API.
- **No SVG input.** SVG must be pre-rasterized to PNG/JPEG or manually decomposed to paths.
- **No table abstraction.** Tables must be built by manually drawing borders and positioning
  text cells.
- **No layout engine.** All coordinates are manual.

#### PDF/UA-1 assessment: CANNOT COMPLY

printpdf cannot produce the `/StructTreeRoot` required for PDF/UA-1. Its object model
does not expose PDF's structure-marking primitives (`BMC`, `BDC`, `EMC` with `/MCID`).
To add tagged PDF support would require either forking the crate or adding a post-processing
step with a separate library. This is not a viable path.

#### Maintenance concern

Development is slow. Issues remain open for extended periods. For a v1.0 quality bar
requiring accessibility compliance, low maintenance velocity on the PDF backend is a risk.

**Verdict: REJECT**

Decisive factors: No PDF/UA-1 structural support. No SVG input. Low maintenance velocity.

### Candidate 2: genpdf / genpdfi (v0.2.0 / fork)

**Author:** Robin Krahl (original), fork maintained separately  
**Latest version:** genpdf 0.2.0 (low activity); genpdfi 0.2.7 (Jan 2026, more active fork)  
**License:** MIT  
**Architecture:** High-level layout engine built on top of `printpdf` + `rusttype`

#### What it can do

- Automatic text layout with line wrapping, paragraph alignment
- Basic table layout (rows/columns, pagination across pages)
- Image embedding (via printpdf's image support)
- Built-in fonts (limited to Windows-1252) or embedded custom fonts
- Simple linear document composition

#### What it cannot do

- **No tagged PDF.** genpdf is built on printpdf, which has no structure tree support.
  Since genpdf abstracts _away_ from printpdf's low-level API, there is no path to inject
  tagged PDF structures even through the underlying layer.
- **No alt text.** No mechanism for `/Alt` entries on figures.
- **No SVG input** (inherited from printpdf).
- **No geometric layout from pre-computed IR.** genpdf produces sequential documents; it
  cannot accept pre-positioned slide-frame IR.
- **No complex script shaping** (rusttype lacks HarfBuzz-level shaping).

#### Architecture mismatch

slideforge's exporter receives `LaidOutDeck` with absolute coordinates. genpdf is a layout
engine — it _computes_ positions. Feeding pre-computed geometry into genpdf requires
fighting the abstraction. There is no "bypass layout, accept coordinates" mode.

#### PDF/UA-1 assessment: CANNOT COMPLY

Same root cause as printpdf — the entire stack has no structure tree support.

**Verdict: REJECT**

Decisive factors: No PDF/UA-1 support (same root cause as printpdf). Architecture
mismatch with LaidOutDeck. No SVG support.

### Candidate 3: Typst as a library (typst 0.14+)

**Author:** Laurenz Villiger and Typst GmbH  
**Latest version:** typst 0.14 (2025), `typst-pdf` crate  
**License:** Apache-2.0 (compatible with our MIT/Apache-2.0 dual license)  
**PDF/UA-1 support:** YES — Typst 0.14 produces tagged PDFs with `--pdf-standard ua-1`

#### Strengths

- **Genuine PDF/UA-1 compliance.** Typst 0.14 generates a `/StructTreeRoot` with proper
  tag hierarchy, `ToUnicode` CMaps, language metadata, alt text from `alt:` declarations,
  and passes PDF/UA-1 checks. This is the only Rust-native solution that ships production-
  grade tagged PDF today.
- **SVG support.** Typst natively embeds SVG files in PDF output. Our `plotters`-generated
  SVG charts would embed correctly.
- **Apache-2.0 license** — fully compatible with MIT/Apache-2.0 dual licensing.
- **Active maintenance** by a well-funded team.

#### Fatal architectural mismatch

Typst is a _typesetting engine_, not a PDF renderer. Its pipeline:

```
.typ source → Typst parser → Typst layout engine → PDF backend
```

The PDF backend (`typst-pdf` crate) consumes Typst's internal `Document` and `Frame`
types — not our `LaidOutDeck`. There is no public API to:

1. Bypass Typst's layout engine and feed pre-positioned IR directly
2. Use `typst-pdf` as a standalone PDF-drawing library

To use Typst, slideforge would need to:

**Option A — Typst Template Approach:** Generate `.typ` source strings from `LaidOutDeck`
(serializing positions via Typst's `place()` function with absolute coordinates), then
invoke `typst::compile()` to produce the PDF. This is feasible but:
- Requires serializing our entire IR to Typst markup — a complex, fragile serialization layer
- Slides use absolute positioning; `place(dx:, dy:)` in Typst does not map cleanly to EMU
  coordinate space with slide-frame semantics
- Typst still runs its layout engine over the result, creating redundant computation
- Debugging a two-layer system (our IR → Typst source → Typst IR → PDF) would be painful

**Option B — Internal API Coupling:** Construct Typst's internal `Document`/`Frame` types
from our IR. This couples `slideforge-pdf` to Typst's unstable internal API, requiring
tracking internal type changes on every Typst release.

#### Dependency weight

Typst brings substantial transitive dependencies including:
- `rustybuzz` (HarfBuzz text shaping — significant compile time)
- Full Unicode database
- SVG renderer (`usvg`, `resvg`)
- Font loading and subsetting stack
- Image decoding for all formats

Expected impact: adds dozens of transitive crates, increases cold build time by
30–90 seconds on typical hardware. Binary size impact is significant.

#### Summary

Typst's PDF/UA-1 output is the gold standard in the Rust ecosystem. However, its
architecture is incompatible with slideforge's Two-IR model. We cannot use it as a
passive PDF renderer for pre-positioned content without either building a complex
serialization layer or coupling to unstable internals.

The template approach (Option A) degrades to generating Typst source strings — effectively
a template-engine integration pattern, not a clean library API. This is viable for a
prototype but not for a production-grade v1.0 where we need precise control over PDF
structure, element placement, and accessibility tagging.

**Verdict: VIABLE (with major caveats) — not recommended as primary approach**

Typst remains a viable _fallback_ or _future path_ if `pdf-writer`+`krilla` cannot meet
PDF/UA-1 validation requirements after Phase 6 hardening. Document as ADR-003 option B.

### Candidate 4: lopdf (v0.32.0)

**Author:** J-F-Liu  
**Latest version:** 0.32.0 (commit 2025-03-20, actively maintained)  
**License:** MIT  
**Unsafe code:** Minimal — pure Rust, no FFI; any unsafe is isolated and contained

#### What it is

lopdf is a low-level PDF object model library for both _reading_ and _writing_ PDFs. It
operates directly against PDF's internal object structure: `Dictionary`, `Array`, `Stream`,
`Name`, `Object`. It is the foundation crate that `printpdf` is built on.

#### Tagged PDF assessment

lopdf is **technically capable** of representing every structure required for PDF/UA-1:

```rust
// lopdf can construct these PDF objects:
//   /StructTreeRoot dictionary
//   /StructElem objects with /S (standard type), /P (parent), /K (children)
//   /RoleMap for custom → standard type mapping
//   /MarkInfo << /Marked true >>
//   /Lang (document language)
//   /Alt (alt text on Figure elements)
//   BMC/BDC/EMC operators in content streams with /MCID tags
```

However, lopdf provides **zero structural support** for building these. Every tagged PDF
element must be constructed manually as raw `Dictionary` objects following the ISO 32000
specification. There is no validation, no convenience API, no type safety around structure
tree invariants.

The effort required to build PDF/UA-1 output on raw lopdf would be equivalent to building
a tagged PDF engine from scratch, using lopdf only for serialization. This is the lowest
possible abstraction level for this task.

**Comparison to pdf-writer:** lopdf has a wider API surface (read + edit existing PDFs)
but less structure for _writing_ new documents. `pdf-writer` provides typed builders that
enforce some invariants and is purpose-built for writing. For slideforge's exporter, which
creates new PDFs from scratch, `pdf-writer` is the more appropriate low-level choice.

**Verdict: REJECT as primary backend**

lopdf would require building a tagged PDF engine from scratch at the lowest possible
abstraction level. `pdf-writer` + `krilla` provide better structure for this work.
lopdf remains useful as a utility for reading/modifying existing PDFs if needed elsewhere
in the pipeline.

### Candidate 5: Headless Browser (Chrome/Playwright)

**Approach:** Generate HTML from `LaidOutDeck`, render HTML to PDF using headless
Chromium (via Playwright's `page.pdf({ tagged: true })`)

#### PDF/UA-1 capability

Chromium 85+ produces tagged PDFs using HTML semantics as the structure source. With
`tagged: true` in Playwright's PDF options, Chromium generates a structure tree from the
DOM. Key findings:

- **Partial PDF/UA-1 compliance.** Simple, semantically structured HTML often passes many
  PDF/UA-1 checks (veraPDF, PAC). Complex layouts (absolute positioning, CSS transforms)
  create reading-order problems.
- **Not guaranteed.** Production reports indicate "many checks pass, but full veraPDF
  clean pass without remediation is unreliable" for non-trivial documents.
- Our slides use absolute positioning (coordinates from `LaidOutDeck`), which is exactly
  the layout pattern that causes reading-order failures in Chromium's tagged PDF output.

#### Visual quality

Excellent for HTML/CSS-native layouts. For 16:9 slide format, `@page { size: 10in 5.625in; }`
works well. Visual fidelity is high.

#### Performance

~1–3 seconds per render on a warm Chromium instance (25-page doc). Cold start adds
~0.5–1 second. Within our 500ms single-deck target for _build_ time this is marginal.
Multiple concurrent renders may be needed for batch use cases.

#### Deployment complexity — BLOCKING

- Chromium binary: **~150–250 MB**. This is incompatible with slideforge's distribution
  model as a single-binary CLI tool.
- Users cannot run `cargo install slideforge-cli` and get a working `slideforge build`
  without separately installing Chrome/Chromium.
- Docker images including Chromium: ~400–800 MB including runtime dependencies.
- Cross-platform distribution (macOS arm64, Windows x86_64, Linux musl) requires
  per-platform Chromium builds or external dependency — fundamentally incompatible with
  our single-binary distribution goal.

This is an architectural non-starter for v1.0 distribution requirements.

**Verdict: REJECT**

Decisive factors: Binary size (150–250 MB) incompatible with single-binary distribution.
PDF/UA-1 compliance unreliable for absolute-positioned slide layouts. External runtime
dependency violates distribution model.

## Recommended Approach: pdf-writer + krilla + custom tagged-PDF layer

### Stack

```
slideforge-pdf crate
├── slideforge_pdf::SlideTagEngine    (custom — tagged PDF structure tree builder)
│   ├── Consumes LaidOutDeck
│   ├── Computes MCID assignments
│   ├── Builds /StructTreeRoot with proper hierarchy
│   └── Sets /Lang, /MarkInfo, /Alt, /ToUnicode
├── krilla (v0.6.0 — experimental tagged PDF layer)
│   ├── Path fills and strokes for shapes
│   ├── Glyph placement for text (with font embedding)
│   ├── Image embedding (PNG, JPEG, SVG)
│   └── Experimental structure element tagging hooks
└── pdf-writer (v0.14.0 — low-level PDF object writer, by Typst author)
    └── Serializes PDF objects to byte stream
```

### Why pdf-writer over lopdf

1. **Active development by Typst's author.** Laurenz Villiger (creator of Typst) maintains
   `pdf-writer` and `krilla`. These crates are part of the same ecosystem that produces
   Typst's gold-standard PDF/UA-1 output. Villiger's PDF knowledge is directly embedded
   in the API design.

2. **Purpose-built for writing.** pdf-writer provides typed builders that guide correct
   PDF object construction — fewer invariant violations than raw lopdf dictionary
   construction.

3. **Version cadence.** pdf-writer 0.14.0 (Oct 2025), 0.13.0 (Apr 2025) — active release
   cadence. lopdf is also maintained (2025-03-20) but has a different scope (read + write).

4. **krilla bridge.** krilla is explicitly built on pdf-writer and provides a mid-level
   drawing API (paths, fills, glyphs, images, gradient). Starting with krilla's tagged PDF
   hooks reduces the amount of boilerplate needed in `slideforge-pdf`.

### What we build in slideforge-pdf

The tagged PDF engine is _slideforge_'s contribution. No Rust crate currently ships a
turnkey PDF/UA-1 API (this is a gap in the ecosystem). We must build:

#### 1. Coordinate Mapping

```rust
/// Convert EMU to PDF user units (points)
/// 1 point = 12700 EMU (from the OOXML spec)
const EMU_PER_POINT: i64 = 12700;

fn emu_to_pt(emu: Emu) -> f32 {
    emu.0 as f32 / EMU_PER_POINT as f32
}
```

Standard 16:9 slide: 9144000 × 5143500 EMU = 720.0 × 405.0 points (10in × 5.625in).

Note: PDF coordinate origin is bottom-left; our IR uses top-left. Y-axis must be flipped:
`pdf_y = page_height_pt - (ir_y_pt + element_height_pt)`.

#### 2. Structure Tree Builder

```rust
/// One document structure tree per LaidOutDeck.
struct StructTree {
    root: StructElem,           // /Document
    page_nodes: Vec<StructElem>,// /Part per slide
    // ...
}

impl StructTree {
    /// Assign MCID numbers and build the structure tree from LaidOutDeck.
    fn from_deck(deck: &LaidOutDeck) -> Self { ... }

    /// Serialize into pdf-writer's catalog.
    fn write_into(&self, pdf: &mut Pdf, catalog_ref: Ref) { ... }
}
```

Structure element type mapping from our `SemanticRole`:

| slideforge SemanticRole | PDF Standard Structure Type |
|------------------------|-----------------------------|
| `Heading(level)` | `/H`, `/H1`–`/H6` |
| `Paragraph` | `/P` |
| `ListItem` | `/LI` with `/LBody` |
| `Figure` | `/Figure` (must have `/Alt`) |
| `Table` | `/Table` → `/TR` → `/TH`/`/TD` |
| `Caption` | `/Caption` |
| `Decorative` | Artifact (excluded from structure tree) |

#### 3. Font Embedding and ToUnicode

Font subsetting and ToUnicode CMap generation are required for both PDF/UA-1 (text
extraction / screen reader access) and for copy-paste to work. We will use:

- `subsetter` crate or `ttf-parser` for font subset extraction
- Custom ToUnicode CMap writer using pdf-writer's stream API

This is the most implementation-complex part of the PDF backend. The work is well-defined
but non-trivial. Estimated effort: 3–5 story-days.

#### 4. SVG Chart Embedding

`plotters` generates SVG. For PDF output, SVG must be converted to PDF vector primitives.
Options:

a) **usvg + resvg path extraction** — convert SVG to a set of paths/fills that krilla can
   draw. usvg is used by Typst internally; it normalizes SVG to a simple path-based model.
   resvg can render to individual shapes. This preserves vector quality in the PDF.

b) **PNG rasterization** — render SVG to PNG at 2x DPI and embed as a raster image.
   Simpler to implement; acceptable visual quality at 300 DPI. Loses scalability.

Recommendation: **usvg + path extraction for Phase 4** (preserves vector quality for
print-quality PDF). PNG rasterization as a fallback for SVG features usvg cannot
decompose cleanly (filters, animation — none expected from plotters charts).

#### 5. PDF/UA-1 Validation Harness

Every slide deck generated by `slideforge-pdf` must pass `veraPDF --flavour ua1` in CI.
Integration test structure:

```rust
#[test]
fn pdfua1_compliance_all_slide_types() {
    let deck = fixture_deck_all_types();
    let pdf_bytes = render_to_pdf(&deck).unwrap();
    assert_pdfua1_valid(&pdf_bytes); // shells out to veraPDF CLI or uses veraPDF Java API
}
```

veraPDF is a Java tool (Apache-2.0 licensed). CI integration via:
- `veraPDF` CLI installed in the CI Docker image
- Rust test calls it as a subprocess: `std::process::Command::new("verapdf")`
- Test fails if any PDF/UA-1 rule violations are reported

## Risk Assessment

### R1 — krilla tagged PDF is experimental (HIGH)

**Risk:** krilla's tagged PDF support is marked "experimental" (v0.6.0). The API may be
insufficient or incorrect for PDF/UA-1, requiring us to build the structure tree at the
pdf-writer level instead.

**Mitigation:**
- S2 code samples (see `S2-code/` directory) validate krilla's tagged PDF API against
  a minimal PDF/UA-1 document structure before committing to it.
- `slideforge-pdf` should be designed so the tagged PDF layer (structure tree builder) is
  independent of the drawing layer. If krilla's tagging is insufficient, we can swap it
  out for direct pdf-writer calls without rewriting the coordinate mapping or glyph
  placement logic.
- Fallback: full structure tree construction at pdf-writer level, using krilla only for
  drawing. This is more work but is a known-good path (Typst itself takes this approach).

**Fallback:** If krilla cannot produce PDF/UA-1-compliant structure trees after Phase 6
hardening, escalate to the Typst template approach (Candidate 3, Option A) with a clear
IR-to-Typst serialization layer.

### R2 — Font subsetting complexity (MEDIUM)

**Risk:** Embedding properly subsetted fonts with valid ToUnicode CMaps is complex.
Incorrect ToUnicode CMaps cause PDF/UA-1 failures (text cannot be extracted) and break
screen readers.

**Mitigation:**
- Use `subsetter` crate (by Typst team, Apache-2.0) for font subsetting — same library
  Typst uses internally.
- Unit-test ToUnicode CMap generation against known-good examples.
- veraPDF CI gate will catch ToUnicode failures before release.

### R3 — SVG-to-PDF fidelity (MEDIUM)

**Risk:** `usvg` path extraction from `plotters`-generated SVG may produce visual
differences vs. SVG rendering in a browser.

**Mitigation:**
- Visual regression tests in CI compare PDF-rendered chart appearance against SVG source
  rendered via headless browser at the same resolution.
- For Phase 4: accept minor anti-aliasing differences. For v1.0 release: require pixel-
  near-identical match for text and line elements in charts (chart data must not change).

### R4 — veraPDF validation infrastructure (LOW)

**Risk:** Installing and running veraPDF in CI adds friction (Java runtime required).

**Mitigation:**
- Use the official `veraPDF/veraPDF-greenfield` Docker image in CI; it includes the full
  veraPDF CLI.
- Local development: `brew install verapdf` on macOS; `apt-get install verapdf` in
  Docker Linux.
- Document in `CONTRIBUTING.md` and the CI `justfile`.

### EMU to PDF coordinate mapping

```rust
// S2-code/coordinate_mapping.rs

/// Standard OOXML measurement unit: 1 inch = 914400 EMU
pub const EMU_PER_INCH: i64 = 914_400;

/// PDF user unit: 1 point = 1/72 inch = 12700 EMU
pub const EMU_PER_POINT: i64 = 12_700;

/// Standard 16:9 slide dimensions in EMU
pub const SLIDE_WIDTH_EMU: i64 = 9_144_000;   // 10 inches
pub const SLIDE_HEIGHT_EMU: i64 = 5_143_500;  // 5.625 inches

/// In points (PDF user units)
pub const SLIDE_WIDTH_PT: f32 = 720.0;
pub const SLIDE_HEIGHT_PT: f32 = 405.0;

#[derive(Debug, Clone, Copy)]
pub struct Emu(pub i64);

/// Convert EMU value to PDF user units (points, 1/72 inch)
pub fn emu_to_pt(emu: Emu) -> f32 {
    emu.0 as f32 / EMU_PER_POINT as f32
}

/// Convert IR top-left origin to PDF bottom-left origin
///
/// IR uses (0,0) at top-left, Y increases downward.
/// PDF uses (0,0) at bottom-left, Y increases upward.
pub fn ir_y_to_pdf_y(ir_y_emu: Emu, element_height_emu: Emu) -> f32 {
    let ir_y_pt = emu_to_pt(ir_y_emu);
    let element_height_pt = emu_to_pt(element_height_emu);
    SLIDE_HEIGHT_PT - ir_y_pt - element_height_pt
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn slide_dimensions_are_correct() {
        // 9144000 EMU / 12700 = 720.0 points = 10 inches
        assert!((emu_to_pt(Emu(SLIDE_WIDTH_EMU)) - 720.0).abs() < 0.001);
        // 5143500 EMU / 12700 = 405.0 points = 5.625 inches
        assert!((emu_to_pt(Emu(SLIDE_HEIGHT_EMU)) - 405.0).abs() < 0.001);
    }

    #[test]
    fn y_axis_flip_origin_at_top_left() {
        // An element at IR y=0, height=100pt should be at PDF y=305pt
        // (slide_height - 0 - 100 = 305)
        let ir_y = Emu(0);
        let elem_h = Emu(100 * EMU_PER_POINT);
        assert!((ir_y_to_pdf_y(ir_y, elem_h) - 305.0).abs() < 0.001);
    }

    #[test]
    fn y_axis_flip_element_at_bottom() {
        // An element at IR y=(slide_height - 100pt), height=100pt
        // should be at PDF y=0 (touching the bottom edge)
        let ir_y = Emu(SLIDE_HEIGHT_EMU - 100 * EMU_PER_POINT);
        let elem_h = Emu(100 * EMU_PER_POINT);
        assert!((ir_y_to_pdf_y(ir_y, elem_h)).abs() < 0.001);
    }
}
```

### Structure tree entry types mapping

```rust
// S2-code/structure_types.rs
//
// Mapping from slideforge SemanticRole to PDF standard structure element types
// per ISO 32000-1:2008 §14.8.4 (Standard Structure Types).

use pdf_writer::types::StructRole;

/// slideforge semantic role for a laid-out element
#[derive(Debug, Clone, PartialEq, Eq)]
pub enum SemanticRole {
    Heading { level: u8 },  // 1–6
    Paragraph,
    ListItem,
    ListLabel,              // bullet/number label for a list item
    Figure,                 // image, chart, diagram
    Table,
    TableRow,
    TableHeaderCell,
    TableDataCell,
    Caption,
    Code,
    Decorative,             // excluded from structure tree (PDF Artifact)
}

impl SemanticRole {
    /// Map to PDF standard structure type name per ISO 32000-1 §14.8.4.
    ///
    /// Returns None for Decorative — these elements are marked as Artifacts,
    /// not as tagged structure elements.
    pub fn pdf_struct_type(&self) -> Option<&'static str> {
        match self {
            SemanticRole::Heading { level: 1 } => Some("H1"),
            SemanticRole::Heading { level: 2 } => Some("H2"),
            SemanticRole::Heading { level: 3 } => Some("H3"),
            SemanticRole::Heading { level: 4 } => Some("H4"),
            SemanticRole::Heading { level: 5 } => Some("H5"),
            SemanticRole::Heading { level: 6 } => Some("H6"),
            SemanticRole::Heading { .. } => Some("H"),   // fallback for level > 6
            SemanticRole::Paragraph => Some("P"),
            SemanticRole::ListItem => Some("LI"),
            SemanticRole::ListLabel => Some("Lbl"),
            SemanticRole::Figure => Some("Figure"),

    /// Returns true if this element must have an /Alt entry per PDF/UA-1.

    pub fn requires_alt_text(&self) -> bool {
        matches!(self, SemanticRole::Figure)
    }
```

### veraPDF CI integration pattern

```rust
// S2-code/verapdf_check.rs
//
// Test helper: validate a PDF bytes slice against PDF/UA-1 using veraPDF CLI.
// Requires: veraPDF installed and accessible as `verapdf` on PATH.

#[cfg(test)]
pub fn assert_pdfua1_valid(pdf_bytes: &[u8]) {
    use std::io::Write;
    use std::process::Command;

    // Write to a temp file — veraPDF requires a file path
    let mut tmp = tempfile::NamedTempFile::new()
        .expect("failed to create temp file for PDF");
    tmp.write_all(pdf_bytes)
        .expect("failed to write PDF to temp file");
    let path = tmp.path().to_str().unwrap().to_owned();

    let output = Command::new("verapdf")
        .args(["--flavour", "ua1", "--format", "text", &path])
        .output()
        .expect("failed to run verapdf — is it installed? (brew install verapdf)");

    let stdout = String::from_utf8_lossy(&output.stdout);
    let pass = stdout.contains("compliant: true")
        || stdout.contains("isCompliant>true");

    if !pass {
        panic!(
            "PDF failed PDF/UA-1 validation:\n\nveraPDF output:\n{}\n\nstderr:\n{}",
            stdout,
            String::from_utf8_lossy(&output.stderr)
        );
    }
}
```

## ADR-003 Input

This spike is the primary input to ADR-003 (PDF Backend Selection). The ADR should
capture:

1. **Decision:** Use `pdf-writer` + `krilla` as the PDF generation stack for
   `slideforge-pdf`. Build a custom tagged PDF engine (`SlideTagEngine`) as the
   PDF/UA-1 layer.

2. **Rejected alternatives and rationale:**
   - printpdf: no structure tree API
   - genpdf: no structure tree API; architecture mismatch
   - lopdf: too low-level; no structural support; `pdf-writer` is strictly better for writes
   - Headless browser: binary size incompatible with single-binary distribution
   - Typst-as-library: architecture mismatch (cannot accept pre-positioned IR)

3. **Fallback trigger:** If `krilla`'s experimental tagged PDF layer cannot produce
   a PDF/UA-1-clean document after a Phase 6 hardening effort of ≤ 5 story-days, escalate
   to either: (a) direct pdf-writer structure tree construction (removing krilla as the
   tagging layer while keeping it for drawing), or (b) the Typst template approach
   (generating `.typ` source from LaidOutDeck).

4. **SVG integration:** usvg (Apache-2.0, by Typst team) for SVG normalization to paths;
   PNG fallback for SVG features usvg cannot decompose.

5. **Validation gate:** Every PDF produced by slideforge must pass `veraPDF --flavour ua1`
   in CI before release. This gate is non-optional per the v1.0 quality bar.
